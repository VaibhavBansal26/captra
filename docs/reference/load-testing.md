# Production load testing

Captra ships a deterministic load harness for the execution paths that must remain healthy under concurrency. It exercises the runtime directly and, when `CAPTRA_POSTGRES_URL` is configured, creates an isolated PostgreSQL schema and includes database and pgvector workloads.

## Run the suites

Build the packages before running the harness:

```bash
npm run build:packages
npm run load:ci
```

The CI profile is intentionally small enough for every pull request. For a release or infrastructure baseline, run:

```bash
CAPTRA_POSTGRES_URL=postgresql://captra:captra@localhost:5432/captra_test \
  npm run load:baseline
```

The command prints a versioned JSON report and exits non-zero when a target is missed. Redirect that output to retain a machine-specific baseline:

```bash
npm run --silent load:baseline > load-report.json
```

## Covered paths

The harness measures:

- concurrent capability execution and correctness;
- simultaneous SSE consumers through the framework-neutral HTTP handler;
- queue throughput across multiple workers;
- recovery after an abandoned worker lease;
- event replay during a reconnect storm;
- PostgreSQL run creation, event persistence, and terminal compare-and-set;
- pgvector persistence and semantic recall;
- process heap growth, maximum per-run event backlog, and database pool waiters.

All capability and embedding behavior is deterministic. The suite never calls a paid model provider.

## Default targets

| Path | P95 latency | Minimum throughput |
| --- | ---: | ---: |
| Concurrent runs | 250 ms | 30 runs/s |
| SSE clients | 500 ms | 20 streams/s |
| Queue workers | 750 ms | 20 jobs/s |
| Reconnect storm | 250 ms | 50 requests/s |
| PostgreSQL | 750 ms | 20 operations/s |
| pgvector | 750 ms | 15 searches/s |

The global error-rate target is zero. Worker lease recovery must complete within 250 ms, heap growth must remain below 128 MB, an ordinary run must not accumulate more than 12 events, and the four-connection database pool must not exceed 64 queued waiters.

These are framework regression gates, not capacity promises for every deployment. Run the baseline profile on the same machine and database class before comparing releases. Provider latency, network placement, application tools, model choice, and database sizing remain application-specific.

## Published baseline

The repository includes [`load/baseline.json`](https://github.com/VaibhavBansal26/captra/blob/main/load/baseline.json), generated by the CI profile with PostgreSQL and pgvector enabled. Treat it as proof that all paths ran and as a report-schema example; use your own repeated baseline runs for production capacity planning.
